# Security

OpenADUC sits in front of Active Directory and writes to it on behalf of operators. The threat surface is "an attacker who can get a session as an OpenADUC admin can do anything that admin can do in AD." Everything below is in service of narrowing that surface.

This document is a high-level summary. Implementation details are in [`apps/api/src/services/`](../apps/api/src/services), [`apps/api/src/plugins/auth.ts`](../apps/api/src/plugins/auth.ts), and [`apps/api/src/lib/encryption.ts`](../apps/api/src/lib/encryption.ts).

## Threat model summary

- **In scope.** Privilege escalation by authenticated users, capability bypass, session theft, audit tampering, secrets extraction from the database, write-as-user impersonation.
- **Out of scope.** Compromise of the host operating system, compromise of the domain controller itself, denial of service, social engineering, and physical security. The dev-mode Samba container shipped for local development is explicitly **not hardened** and should never be used in production.

## Authentication

Operators sign in with their Active Directory username and password. The API performs a live LDAPS bind against a domain controller — there is no in-app password hash and no local password store.

Every failed sign-in gets the same answer, whatever AD said (unknown user, wrong password, locked, disabled, expired, or no OpenADUC role), and directory outages don't reveal hosts or error text. The specific reason is recorded in the audit log. Step-up failures follow the same rule.

There is no local break-glass account yet: if every domain controller is unreachable, or no one is left in a role group, nobody can sign in until that's fixed in AD.

## Sessions

Successful sign-in mints an `admin_sessions` row and a signed cookie. The session stores a **snapshot** of the operator's capabilities, resolved from their AD group memberships at sign-in.

Every step-up re-reads those memberships from the fresh bind and replaces the snapshot. An operator removed from a role group loses that role's capabilities at their next step-up, and one left with no role is signed out. Stepping up never extends the session's absolute expiry. The worst case for a removed operator is therefore: write access until their current elevated session ends (see [step-up](#step-up-authentication)), and read access until the session itself ends (idle or absolute timeout below). To cut access immediately, disable the AD account: binds then fail, so they can't step up again.

Two timeouts apply, both configurable:

- **Idle timeout** (`SESSION_IDLE_TIMEOUT_MINUTES`, default 60 min) — sliding window, refreshed on every authenticated request.
- **Absolute timeout** (`SESSION_ABSOLUTE_TIMEOUT_HOURS`, default 12 h) — hard cap from sign-in regardless of activity.

The session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, and signed with `SESSION_COOKIE_SECRET`. Rotating that secret invalidates all sessions.

## Capabilities

Authorization is capability-based, not role-based at the call site. Each route declares a policy, the capability it needs (`config: { policy: { capability: 'write:user.resetPassword', stepUp: true, directory: 'caller' } }`), and the auth plugin checks it against the actor's snapshot. Roles (`admin`, `operator`, `auditor`) are convenience bundles defined in [`packages/shared/src/capabilities.ts`](../packages/shared/src/capabilities.ts) — adding a role is a config change, not a code change.

Each role is granted to the **direct** members of one AD group; nested membership isn't followed yet. First-run setup grants admin only to a direct member of the admin group: `BOOTSTRAP_ADMIN_GROUP_DN` when set, otherwise Domain Admins. It checks this before anything is saved; whoever reaches a fresh install first can't make themselves admin with an ordinary domain account. The later setup steps require the admin capability, and once setup is done the public status endpoint reveals only that it's done.

The capability set is intentionally fine-grained (`read:user`, `write:user.resetPassword`, `write:user.unlock`, `write:user.attributes`, `write:group.membership`, `configure:directory`, `view:audit`, `view:raw_attributes`, etc.) so that giving someone "the ability to unlock accounts" doesn't also give them "the ability to reset passwords." A password reset can also clear the account's lockout in the same directory change; asking it to needs `write:user.unlock` as well, checked and audited like the route's own capability. Setting or clearing when an account expires takes `write:user.enableDisable`, not `write:user.attributes`: an expiry decides whether the account works just as enabling does (AD keeps `accountExpires` and `userAccountControl` in the same Account Restrictions property set), so someone who may only edit attributes can't revive an expired account. Clearing "password never expires" writes `userAccountControl` as enabling does, so it takes `write:user.enableDisable` too. Making a user change their password at next sign-in (`pwdLastSet` 0) is half of a password reset, and ADUC's delegation wizard grants the two together, so it takes `write:user.resetPassword`.

Three writes carry extra guard rails because they're hard to undo:

- **Delete** (`write:user.delete`, admin role only) works on disabled accounts only, and never on accounts AD marks `isCriticalSystemObject` or creates for itself (RID below 1000: Guest, krbtgt, DefaultAccount, …). The API re-checks both against the live entry immediately before deleting, and each request must repeat the account's sAMAccountName, so a stale list or a wrong id can't delete the wrong person. The audit row keeps the account's attributes and group memberships, which is the only record left on domains without the AD Recycle Bin.
- **Rename** (`write:user.rename`, admin and operator) changes how a person signs in: cn, sAMAccountName, userPrincipalName and the primary SMTP address. New values are checked for collisions across the domain before anything is written, and if the attribute write fails after the cn has changed, the cn is renamed back.
- **Group delete** (`write:group.delete`, admin role only; map another group to the admin role, or change the role bundles, to grant it more widely) refuses:
  - critical system objects (`isCriticalSystemObject`);
  - built-in groups: in `CN=Builtin`, flagged builtin in `groupType`, or a well-known RID below 1000;
  - groups AdminSDHolder protects (`adminCount=1`);
  - groups mapped to an OpenADUC role, which would lock that role out;
  - groups directly in a protected group (Administrators, Account/Server/Print/Backup Operators, Replicator, Domain Admins, Domain Controllers, Schema Admins, Enterprise Admins, Read-only Domain Controllers, Key Admins, Enterprise Key Admins, recognized by well-known SID, or any `adminCount=1` group), since AdminSDHolder may not have flagged them yet. DnsAdmins and DnsUpdateProxy have no well-known SID, so only their `adminCount` protects them;
  - groups that are some account's primary group (`primaryGroupID`), which AD refuses anyway.

  The API checks these against the live entry, its parent groups and AD's primary-group count, again on the operator's own bind immediately before deleting, and audits a refusal as a failed `group.delete` with the reason. Each request must repeat the group's pre-Windows 2000 name. The audit row keeps the group's members and parent groups, which a tombstone doesn't.

Importing users from a spreadsheet takes what creating them does: `write:user.create`, plus `write:group.membership` when a bucket adds groups, and step-up, with `configure:security` for a role group as above. The wizard keeps its draft in the browser's session storage, never on the server; before the final check it only reads: the naming check, and `POST /api/users/import/lookup` (`read:user`), which asks AD, not the cache, who holds the rows' employee IDs, emails and manager values. A spreadsheet's columns map only to a fixed list of fields, never to raw LDAP attributes. The final check (`POST /api/users/import/check`) writes nothing but takes the run's capabilities and step-up: it judges each row's names by the naming pattern's rules, checks them against each other and against AD exactly as they'll be written, checks each email against whoever holds it in AD and against the other rows' emails and UPNs, looks again for someone already holding a row's employee ID or email, checks in one search that each OU, group and manager still exists in AD, and lists the groups AD protects so the run can ask for acknowledgement. Placement rules, saved when an import runs, where it last put the bucket for a value in the column it grouped by, are stored per directory (`GET`/`PUT /api/directories/:id/placement-rules`, `write:user.create`, saving with step-up), and each one added or changed writes an `import.placementRule.create` or `.update` row with its before and after.

Running an import (`POST /api/users/import/run`, the same capabilities and step-up) runs the final check again and refuses, writing nothing, if it finds anything, or if rows go in a group AD protects without the acknowledgement. Otherwise it starts a bulk job, one row per account, each audited as a single create is, with the job's id: the account is created disabled, gets its password, is enabled if asked, is added to its bucket's groups (one `user.group.add` row each), then gets its manager (`user.update`). A row whose manager the import creates waits for that manager's row. A step failing after the create leaves the account as it is and the row partial, naming the steps (and groups) that failed; a retry runs only those, never the create. An account created but not read back is looked for again (by id, DN, then the logon name and UPN written); one still not found leaves the row partial with what's left. A retry of a row with no record of its create (the run died after the add) takes on the account only if it has exactly the row's logon name and UPN, is still disabled and was created after the job started; otherwise the create fails as a name taken.

In generate mode the server makes each row's password and, in set mode, keeps the one typed (which can't start with `=`, `+`, `-` or `@`); either is held encrypted in `import_passwords`, bound to its job and row as associated data so a ciphertext can't be moved to another, never in the job's rows, its subject or any audit row. Only the job's operator can download the results CSV (`POST /api/bulk-jobs/:id/results`, the job's capability and step-up), once the job has stopped, once, within `HELD_PASSWORD_HOURS` (24) of each password being stored or the job last finishing: the download takes the passwords and writes its `bulk.results.download` row in one transaction, a refused download is audited as a failure, and the sweep purges what isn't downloaded in time. The CSV holds each password exactly, never altered by formula neutralisation, as none can start like a formula. A row that only gets its password after the download, or once the shared one has expired, gets a random one, recorded on the row and its audit row (`passwordMode: random`), and the results page marks it as needing a reset. In random mode the CSV has no passwords and can be downloaded again. An import can't be reverted: disable or delete the accounts instead.

Once an import's passwords are downloaded or purged, its results page offers to reset them: `POST /api/users/bulk-reset-passwords` (`write:user.resetPassword`, step-up) takes only the import's id, and its rows are that import's created accounts, if the import is the operator's own. Each row makes a password to the domain's policy, holds it as above before setting it, and resets the account with must-change, audited as a single reset is; its CSV hands the passwords out the same way, once. A reset can't be reverted.

Issuing a Temporary Access Pass (`POST /api/users/:id/temporary-access-pass`, `write:user.issueTap`, step-up) creates one in Microsoft Entra for the user's synced account through the directory's Entra integration. Its `temporaryAccessPass` feature is off until an administrator turns it on and grants the app registration `UserAuthMethod-TAP.ReadWrite.All` (narrower than `UserAuthenticationMethod.ReadWrite.All`), `Policy.Read.AuthenticationMethod`, `User.Read.All` and `RoleManagement.Read.Directory`; the connection test fails, naming the permission, while a turned-on feature lacks one. Whoever holds a pass can sign in as the user, so it has its own capability rather than riding on `write:user.resetPassword`. Admins and operators have it, as walk-ins and reissues are helpdesk work, and turning the feature on is the opt-in.

The API refuses, with the reason, anyone who administers AD, OpenADUC or Entra, and anyone it can't clear of that:

- **AD groups**, nested membership included, read from the user's `tokenGroups`. A well-known SID decides by itself, in any domain of the forest, so Enterprise and Schema Admins from the forest root count for a child domain's user and Domain Admins counts with a base DN that's an OU: Domain Admins, Domain Controllers, Schema Admins, Enterprise Admins, Group Policy Creator Owners, Read-only and Enterprise Read-only Domain Controllers, Key Admins, Enterprise Key Admins, and the Builtin Administrators, Account, Server, Print and Backup Operators and Replicator. The other groups are looked up from the domain's root: one AdminSDHolder has flagged (`adminCount=1`), one mapped to OpenADUC's admin role, or a group named DnsAdmins in `CN=Users` (it has no well-known SID, so a renamed or moved DnsAdmins isn't recognised) refuses. A group that can't be found there (from another domain, say), or `tokenGroups` that AD doesn't return, refuses too, as does the account's own `adminCount=1`.
- **Entra roles**: a directory role the user holds, or any active role assignment or Privileged Identity Management eligibility (custom and administrative-unit-scoped roles included) for the user or a group they're in, read tenant-wide from `roleManagement/directory`. If Graph won't list them, or they run past 50 pages, the user is refused as unverified; a tenant without Entra ID P2 or Governance, which Graph refuses eligibilities to (`AadPremiumLicenseRequired`), has none to find, so only its assignments count. A role reached only through an eligible membership of a group (PIM for Groups) isn't seen.

The Entra account is found by the AD account's SID (`onPremisesSecurityIdentifier`), never by UPN, which a cloud-only account could share. The lifetime and the one-time setting must fit the tenant's Temporary Access Pass policy, read from Graph at most once a minute, and the start must be within 30 days. A policy that's turned off refuses, and a user outside the policy's targets is warned about, not refused. A pass the user already holds is replaced only when the request says the operator was warned, and a request Entra rejects is answered with Entra's reason (422). The value is in the response alone (`Cache-Control: no-store`): it's never stored or logged, `temporaryAccessPass` is redacted from logs and audit rows wherever it appears, and the `user.tap.issue` audit row records the start, lifetime, one-time setting and Entra user id. A refusal is audited as a failed `user.tap.issue` with its reason.

An import can issue each new hire a Temporary Access Pass for their onboarding class ("Issue TAPs for class"; why the values are stored is [ADR 0003](adr/0003-class-taps-are-stored-until-they-expire.md)). Scheduling one takes `write:user.issueTap` on top of what the import takes, and the final check, run after step-up, holds the class's lifetime and use, and a single start, to the tenant's policy; a person whose start date is more than 30 days off has their pass made once it's within reach. The passes are made later by a follow-up in the API process (`services/classPasses/`), without the operator: Graph is called with the app's client credentials and AD read with the service account, never with an operator's password. It acts on its **authoriser**'s authority, the import's operator at first: every quarter of an hour it checks that they're still in AD, enabled, and in a group whose role grants `write:user.issueTap`, and pauses the class when they aren't (the roster and the import's page say so, `import.class.pause`). Any operator with `write:user.issueTap` can then take the class over after step-up (`.../take-over`, `import.class.takeOver`), and rescheduling makes whoever reschedules the authoriser too. Each pass is made only for an account the import created (by its row, so by objectGUID), for the class as scheduled, and refused, as Issue TAP refuses, to anyone who is or may be an administrator. That's checked again daily and two hours before class, and before every reveal: a holder who has become one, or can't be cleared, has their pass deleted in Entra (`DELETE …/temporaryAccessPassMethods/{id}`, under the same permission), its value deleted, and their row refused with the reason (`import.classPass.revoke`); a reissue refused the same way deletes the pass they held. A reschedule or reissue deletes the person's pass in Entra before making the new one, and the stored value at once, so a new pass that can't be made (class over, outside the policy, refused) leaves no old one behind. A pass the class didn't make (one the help desk issued) isn't replaced: the row says so, and a reissue, after the operator confirms, replaces it. A pass Graph made but OpenADUC couldn't store, with its audit row, is deleted in Entra again and made later. Graph returns a pass's value once, so it's stored encrypted, bound to its job and row, until the pass expires, is used or replaced in Entra (as the roster or the follow-up finds), or class is rescheduled; before class it can't be used, as Entra enforces the start. The class roster (`GET /api/users/import/jobs/:id/class-roster`) is open to any operator with `write:user.issueTap` in the import's directory, not only the import's operator; it writes nothing and asks Graph about each pass at most once a minute, not at all while Graph throttles the directory. Revealing a pass (`.../:rowId/reveal`, `Cache-Control: no-store`), reissuing one (`.../:rowId/reissue`) and rescheduling class (`.../reschedule`) take step-up, and each is audited (`import.classPass.reveal`, `import.classPass.reissue`, `import.class.reschedule`), never with the value; passes made by the follow-up are audited as `import.classPass.issue` under the authoriser, with `system` as the method. Turning the directory's `temporaryAccessPass` feature off, or removing its Entra integration, deletes every class pass value OpenADUC holds for the directory within a sweep (30 seconds) and stops the follow-up; the passes already in Entra are left to expire as they were set to, so delete them in the Entra admin center if they must stop sooner. The roster still opens, to say so.

Licenses are read-only: OpenADUC never assigns or removes one. The Entra integration's `licenses` feature is off until an administrator turns it on and grants `User.Read.All`, `Group.Read.All` and `Organization.Read.All` (the tenant's subscriptions, for products Microsoft's name list lacks, and its last sync, for an object not synced yet); `Directory.Read.All` covers all three, and the connection test names any it lacks. A user's licenses (`GET /api/users/:id/licenses`, `read:user`) and a group's (`GET /api/groups/:id/licenses`, `read:group`) are read live, the Entra object found by its AD SID as for a Temporary Access Pass. Group pickers badge licensed groups from `entra_group_licenses`, which the `entra.licenses.groups` task fills hourly and a group's page updates for that group (`GET /api/groups/licensed`, `read:group`, which also says when the task last read Entra and whether its latest run failed); it holds Entra group ids, names, SIDs and SKU ids, nothing about users. An import's final check reads the tenant's seats live (`/subscribedSkus`) to warn of a product its groups grant to more people than it has free, and the cache with the AD group nesting to warn of a bucket group that's only inside a licensed group; neither stops the run. Once an import's people have synced, its license follow-up reads each one's `licenseAssignmentStates` (`User.Read.All`) with the app's client credentials, finding them by SID; it holds their Entra id and each license's state and error, and writes nothing to Entra or AD. A Graph call that's throttled (429, or 503 for a read) waits as Graph's `Retry-After` asks, up to three retries and ten seconds in all, then answers 503 `entra_throttled`.

Creating a group (`write:group.create`, admin and operator) checks its name among the OU's children and its pre-Windows 2000 name across the domain, both before the operator submits and again on the operator's own bind before writing.

Creating a user (`write:user.create`, admin and operator: onboarding is the most common helpdesk task after password resets) checks the sAMAccountName, UPN and email across the domain and the CN among the OU's children, before the operator submits and again on the operator's own bind before writing. It follows AD's order: the account is added disabled, then gets its password (with must-change, in the same modify, which also clears PASSWD_NOTREQD), then is enabled as exactly a normal account. A step that fails after the add leaves the account disabled, and the response and the failed `user.create` audit row say which steps remain and record the account's `whenCreated` and `uSNChanged`. `POST /api/users/:id/finish-create` runs the remaining steps only within 24 hours of the create and only while the account is as the create left it (same `uSNChanged`; read from another domain controller, at least still no password and no sign-in), so it can't reset and enable an account someone has since set up or disabled by hand; each finish row records the create's correlation id. In the random password mode the API generates a 32-character password and never returns or records it; must-change is off in that mode, because `pwdLastSet=0` stops a synced user signing in to Entra unless Connect Sync's force-change flag is on. Phone numbers are written in Entra's `+CC NUMBER` form; one that can't be read is refused unless the request names it in `keepPhonesAsTyped`. `proxyAddresses` is never written.

Copying a user (`GET /api/users/:id/copy`, then the same create) carries over the source's OU, organisation attributes (title, department, company, manager, office, address, and the country as `c`, `co` and `countryCode` together) and direct groups, never its names, email, phones, employee IDs or description. The copy endpoint needs `write:user.create`, since it says which groups map to OpenADUC roles, and records a `user.view` of the source like the detail page. Adding the copy to groups also needs `write:group.membership`, checked on the server for the create and for a finish that still has groups to add. The groups are added after the password and before enabling, one by one: a group AD refuses doesn't stop the others, but leaves the account disabled with the groups step remaining, and the create's audit row lists the groups still to add for finish-create to retry. A group still to add that no longer exists (gone from the cache or from AD) is left out, reported as `groupsSkipped` in the response and the audit row, so it can't hold the account back. Groups that grant administrative rights (protected by AdminSDHolder or flagged `adminCount=1`, or mapped to an OpenADUC role) are offered unticked with a warning rather than refused, so copying an admin's template stays possible but is a deliberate choice; a role group is offered only to an operator with `configure:security` (see below), shown disabled with the reason to anyone else. AD's own permissions still decide. The `user.create` row records the source (`copiedFrom`) and the groups asked for; in the same correlation each group add writes a `user.group.add` row and the source gets a `user.copied` row naming the copy. Those follow-on rows are logged rather than failing the request if they can't be written, as the write has already happened.

Computer accounts can be disabled and enabled (`write:computer.enableDisable`), moved (`write:computer.move`) and reset (`write:computer.resetAccount`), all three admin and operator. Reset works as ADUC's Reset Account does: the password becomes the lowercase computer name without the `$`, cut to 14 characters, which is what a computer rejoining under the same name tries. The domain password policy doesn't apply to machine accounts, so the short password is accepted; the operator needs the Reset Password right on the computer. Until it rejoins, the computer can't authenticate to the domain, so the UI asks first. Disable, reset and move refuse domain controllers (`SERVER_TRUST_ACCOUNT`), read-only domain controllers (`PARTIAL_SECRETS_ACCOUNT`) and anything AD marks `isCriticalSystemObject`, checked against the live entry and again on the operator's own bind; the refusal is audited with the reason, and neither UI offers those actions on such a computer.

A failed capability check returns 403 and writes an `authz.deny` row to the audit log with the required capability, the actor, and the request correlation id.

Adding members to a group mapped to an OpenADUC role hands them that role at their next sign-in (members of a group nested in it too), so it takes `configure:security` as well as `write:group.membership`. The server checks it on the single-member routes (`/api/users/:id/groups`, `/api/groups/:id/groups`) and on a bulk add when it starts, continues or is retried; the refusal names the group and the role, and writes an `authz.deny` row with the capability and that reason. Taking members out takes nothing more. A bulk add to a group AD protects (AdminSDHolder, or `adminCount=1`) also needs the operator to tick that these users gain admin rights in AD: without it the API refuses the job (422) before writing anything. Creating or copying a user into a role group takes it too, checked on the create and on a finish-create that still has groups to add. AD's own permissions still decide every change.

## Step-up authentication

Mutating routes require **step-up auth**: the operator re-enters their AD password, the API rebinds against the directory, and on success mints an `elevated_sessions` row with a write-only subset of capabilities.

The elevated session ends at whichever comes first:

- **Idle timeout** (`stepup.idle_timeout_minutes`, default 15 min): every authenticated request from the operator pushes it back. Requests the SPA makes by itself, polling a running sync task, are marked `x-background-request: 1` and don't count. To spare the database, a request that would move it by less than a twentieth of the timeout isn't recorded, so the session can end up to that much early.
- **Absolute lifetime** (`stepup.absolute_lifetime_minutes`, default 4 h): counted from step-up, however active the operator is. An elevated session also never outlives the session it belongs to: its idle timeout is capped by the session's, and its absolute end by the session's.

Both are policy settings (**Settings → Policy**). Changing them requires step-up and writes a `settings.update` audit row; a new idle timeout applies to open elevated sessions at their next request, a new absolute lifetime from the next step-up.

The web UI has no mode to enter (see [ADR 0001](adr/0001-step-up-without-edit-mode.md)). Write-capable operators always see editable fields and actions, and dialogs open without step-up; a write without an elevated session prompts step-up and then completes. While an elevated session lives, a quiet indicator by the operator's name in the sidebar (in the Old School view, the status bar) says when it ends if idle and lets them end it at once. When it ends, unsaved edits stay on screen and the next save prompts step-up again.

The operator's password is held only in process memory in `CredentialCacheService`. It lives in a `Buffer` that is zeroed on eviction, is evicted when the elevated session ends by either limit (a sweep every few seconds catches an operator who never comes back), and is never written to disk or the database. An API restart wipes all cached passwords, forcing re-step-up — which is intentional.

**Bulk jobs** (bulk disable, enable and unlock, bulk add to or remove from groups, bulk attribute edits, bulk moves, and bulk account expiry, must-change and clearing "password never expires") run on the server, so they carry on when the operator closes the tab, and hold no credentials of their own. Before each row, a job looks up its operator's elevated session and the password cached for it, as a request does. Once that session has ended (idle, at its absolute lifetime, by step-down or sign-out, or because the API restarted), the job pauses before its next row and says it needs step-up; it continues only when the operator steps up and continues it, which moves it onto the new elevated session. A job's own writes don't count as activity, so it can't keep an unattended elevated session alive. Starting, continuing or retrying a job takes the action's capability and step-up; stopping one takes neither, since it only prevents writes. The jobs API shows a job only to its operator; anyone else sees it in the audit log. Reverting a job (its preview, `GET /api/bulk-jobs/:id/revert/preview`, and `POST /api/bulk-jobs/:id/revert`) starts a new job, the reverting operator's own, and takes what the job's own writes take (the action's capability, `configure:security` to put users back in a role group) and step-up; reverting another operator's job also takes `view:audit`, since that's where it's seen. So an auditor can't revert, and an operator without the audit log reverts their own jobs from the job's panel once it has stopped. A job can be reverted once it has stopped and none of its rows are still running (a stop lets rows in flight finish). Only one revert of a job can be under way at a time, a stopped revert with rows still running counting as under way, and the job can't be retried meanwhile: starting a revert and retrying either job lock the reverted job's row, and a partial unique index backs that up (409). A revert can't itself be reverted. Putting users back in a group AD protects (AdminSDHolder) takes the same tick that they gain admin rights as a bulk add does, without which the API refuses the revert (422).

This is what enables **write-as-user**: every AD modification is bound as the operator, not as a shared service account, so AD's own audit log attributes the change to the right human.

## Audit

Every authenticated action — successful or denied — produces an `audit_events` row. The table is append-only at the database level: a trigger rejects `UPDATE`, `DELETE`, and `TRUNCATE` on the table, so even a compromised application cannot silently rewrite history.

Each row captures: action, actor, target type and id, before/after JSON snapshots, source IP, user agent, session id, correlation id, error code, and arbitrary metadata. Keys matching a sensitive-key allowlist (`password`, `secret`, `token`, etc.) are auto-redacted to `[REDACTED]` before insert.

Every event a bulk job writes carries the job's id (`bulk_job_id`): its `bulk.create` event, one event per row in the same shape as the single-object write's, and any `bulk.pause`, `bulk.resume`, `bulk.retry` or `bulk.cancel`. A group job writes one event per user and group, a no-op included (a user already in the group, recorded with before and after alike, as the single-member route records one), so its events account for every row `bulk.create` counted. A bulk attribute edit (`write:user.attributes`) reads each user live before writing, writes only the fields not already as asked, and records the same `user.update` event as the single-user edit; a user already as asked gets one too, marked `unchanged`, with before and after alike. A user the edit would make their own manager is skipped, and the row says why. A bulk move, account expiry, must-change or clearing of "password never expires" makes, per user, the write and `user.move`, `user.accountExpiry.set`, `user.passwordMustChange.set` or `user.passwordNeverExpires.clear` event the single-user write does, after reading the user live; a user already as asked isn't written, and gets the event marked `unchanged`, with before and after alike, as a single-user move or expiry to what the user already has does too. A move, single or bulk, only goes to an OU the cache knows and its last full sync saw, never to Domain Controllers (AD's own system OU, refused with 422); a name the OU already holds is refused by AD as a conflict (409, or a failed row naming the object), and the bulk preview flags those users first. Any attribute edit, single or bulk, refuses a manager that isn't a user in the directory, or is the user itself, before writing. The audit log shows the job as one expandable entry.

A revert is a job of the opposite action (a revert of a bulk disable is a `user.enable` job), its `bulk.create` event naming the job it reverts (`revertsJobId`), and the reverted job's entry says who reverted it and when. It considers only the rows the job changed (succeeded, or partly); for each, it reads the user live, compares what the job's row recorded changing with what they have now, and makes the single-user write that puts the before-values back, audited as that write is: `user.enable` or `user.disable`, `user.group.remove` or `user.group.add` (only the groups the row changed; a primary group the job recorded as already done isn't touched), `user.update` (only the fields it changed), `user.move` (back to the OU the user came from, refused when that isn't an OU, such as `CN=Users`), `user.accountExpiry.set`, `user.passwordNeverExpires.set`, or `user.passwordMustChange.clear`. That last sets `pwdLastSet` to -1, which AD turns into now: AD keeps no earlier value to go back to, so the password's age restarts. An unlock can't be reverted, since AD can't lock an account again. Moves and manager edits record the OU's and the manager's GUID, and a revert finds them by it, so an OU or manager renamed or moved since is neither "changed since" nor missing (rows recorded before that compare by DN). A user changed again since the job is skipped, its row saying so (`changed_since`), unless the operator included them after the preview listed them: a field, the OU or the expiry no longer what the job left; or, though it is, the account written again since. For that, each row keeps the account's `uSNChanged` as read back after its write, and a different one now counts (it's per domain controller, so read from another DC it counts too, and so does any later change to the account, a sign-in's `lastLogonTimestamp` included: the preview says so, and the operator can include the user). Memberships, which change the group rather than the account, and rows from before `uSNChanged` was kept, count OpenADUC's own events on the user since the row ran, other than the job's and its reverts'; a membership changed and changed back outside OpenADUC can't be seen. A user already back as they were is skipped too. An expiry the job couldn't read back is reverted, the preview saying what it left couldn't be checked.

Each row also names the directory it belongs to: the one the action targeted, else the one the operator was signed in to. The audit log shows an auditor only their own directory's rows, plus installation-wide ones (settings changes, first-run setup), which name no directory and appear in every directory's log.

Audit retention is unbounded by default. Operators can prune older rows out-of-band if needed, but the application will not.

## Encryption at rest

Secrets stored in Postgres are encrypted with **AES-256-GCM** using `ENCRYPTION_KEY`. Affected fields:

- `directory_providers.bind_secret_encrypted` — service account password.
- `directory_entra_integrations.client_secret_encrypted` — Entra app secret (when configured).
- `directory_entra_integrations.teams_webhook_url_encrypted` — Teams webhook URLs.
- `import_passwords.password_enc` — the passwords an import or a password reset hands out, bound to their job and row, until its results CSV is downloaded or `HELD_PASSWORD_HOURS` pass.
- `class_passes.pass_enc` — an import's class Temporary Access Passes, bound to their job and row, until each expires, is used or replaced, or the directory's feature is turned off.

Ciphertexts are stored as `v1.<iv-b64url>.<ct-b64url>.<tag-b64url>`. The version prefix lets us migrate to a new construction or key without breaking older rows. Losing `ENCRYPTION_KEY` makes these rows undecryptable; **back it up alongside your database backups**.

The operator step-up password is **never** encrypted to disk — it only lives in process memory.

## AD-specific risks

Some risks are inherent to writing to AD; OpenADUC mitigates them but cannot eliminate them.

- **Account lockouts via `lockoutTime` writes.** OpenADUC's unlock endpoint zeroes `lockoutTime` rather than incrementing `badPwdCount`. A buggy or malicious caller using raw attribute write would still be capability-gated by `write:user.attributes` and audit-logged.
- **Password reset replication delay.** A password reset against one DC may take seconds to replicate; the API does not poll for replication. The audit row records which DC was written to.
- **Service account scope.** The bootstrap service account only needs read for sync. Write capabilities (`User-Force-Change-Password`, `Reset Password`, `Account Restrictions`) should be **delegated on the OUs you intend to manage**, not granted forest-wide. The setup wizard's documentation links walk through the recommended delegations.
- **Secrets the service account can read.** Sync reads every attribute the service account is allowed to see. If it can read LAPS passwords (legacy `ms-Mcs-AdmPwd` or Windows LAPS), gMSA passwords or BitLocker recovery keys, OpenADUC drops them as they're read: they are never cached, returned by the API or shown. Even so, don't grant the service account those rights.
- **Raw attributes.** The full attribute set of users, computers, deleted objects and GPOs (the Raw LDAP tab and the old-school Attribute Editor) is returned only to holders of `view:raw_attributes` (admins by default). Other readers get typed fields only, and the raw tabs are hidden.
- **LDAPS certificate validation.** Production deployments must keep `AD_TLS_REJECT_UNAUTHORIZED=1`. Setting it to `0` (only valid for the local Samba dev container) disables hostname verification and exposes operator credentials to MITM.
